## cc.1 Compile-time feature gating with real dead-code elimination

- **where:** scripts/defines.ts (35 enabled / 8 commented-out entries), scripts/vite-plugin-feature-flags.ts (the transform), consumed across 237 files / 1,015 call sites in src/ and packages/
- **what:** Gated code calls `feature('FLAG')` imported from the virtual module `bun:bundle`. A pre-bundle transform rewrites the call to the boolean literal `true`/`false`, so the bundler sees `if (false) { ... }` and strips the branch. The transform deliberately runs BEFORE import resolution, because gated blocks are allowed to `require()` files that do not exist — the bundler must never try to resolve them. Disabled features are commented out of the registry with an inline reason.
- **how:** `FEATURE_CALL_RE = /feature\s*\(\s*['"]([\w]+)['"]\s*\)/g` in a Rollup `transform()` hook that returns early for node_modules; `bun:bundle` is resolved as a virtual module id and stubbed with `return false` for the non-Vite path.
- **solves:** Lets a single 715k-line source tree ship many product variants (voice, bridges, coordinators, LSP, channels) without runtime `if` overhead or dead imports, and lets an operator cut a whole subsystem at build time.
- **port effort:** Low to implement (one ~90-line plugin + a const array). High to adopt safely — this repo shows the failure mode: 59 of 94 flags drifted out of the registry and are silently always-false. | **idea only:** True
## cc.2 Ports-and-adapters workflow engine with deterministic journal replay

- **where:** packages/workflow-engine (42 files / 5,791 lines), entry `packages/workflow-engine/src/tool/WorkflowTool.ts` gated on FEATURE_WORKFLOW_SCRIPTS; documented in docs/features/workflow-scripts.md
- **what:** A standalone orchestration engine that runs a plain JS script (compiled by Bun's transpiler) with primitives `agent()`, `phase()`, `parallel()`, `pipeline()`. The non-deterministic parts — the LLM, the filesystem, the clock — are isolated behind injected ports, so the same script produces the same journal on every replay. Core layer has zero runtime dependencies.
- **how:** `WorkflowPorts` interface + `createHostHandle` / `createFileJournalStore` adapters; only `ajv` and `zod` as runtime deps.
- **solves:** Makes multi-agent orchestration replayable and testable: a run is a pure function of (script, ports), so a flaky multi-agent workflow can be re-driven from its journal instead of re-run.
- **port effort:** Medium — the architecture is portable but the implementation must be rewritten, not copied (see the licensing finding). | **idea only:** True

## cc.4 Post-bundle source rewriting for runtime compatibility

- **where:** build.ts steps 3a/3b (string replace over every emitted .js); the Vite path does the same job with plugins (scripts/vite-plugin-import-meta-require.ts)
- **what:** After bundling, the output is regex-patched in place: `var __require = import.meta.require` becomes a guarded createRequire fallback, and unguarded `var {…} = globalThis.Bun` destructuring from third-party deps is made conditional so Node does not crash at import time.

- **solves:** Makes one bundle genuinely dual-runtime without forking third-party dependencies.
- **port effort:** Low. Note it is duplicated across two bundlers in this repo — a port should keep it in exactly one place. | **idea only:** True

## cc.9 Declarative-only plugin model (no in-process code)

- **where:** /Users/tranquangdang21/Projects/claude-code-ref/src/utils/plugins/schemas.ts:886 (PluginManifestSchema, no entrypoint field); verified by `rg 'await import\('` over src/utils/plugins/*.ts returning only fflate + @anthropic-ai/mcpb
- **what:** A plugin is a directory of markdown + JSON + subprocess argv definitions. There is no JS/TS entrypoint, no module evaluation, no object graph with methods.
- **how:** Manifest declares paths; loader reads files; components are registered as data into AppState / STATE.registeredHooks.
- **solves:** Removes the entire class of plugin-supply-chain RCE in the host process. A malicious plugin can only spawn a subprocess or make an HTTP request — never run in the CLI's address space, never monkey-patch internals, never exfiltrate the host's memory.
- **port effort:** High effort, high payoff. This is the load-bearing decision of the whole design; everything else is bookkeeping. Rejecting arbitrary in-process code is what makes plugin trust tractable. | **idea only:** True

## cc.14 Secrets never reach the model context

- **where:** /Users/tranquangdang21/Projects/claude-code-ref/src/utils/plugins/pluginOptionsStorage.ts:369-399
- **what:** `substituteUserConfigVariables` (for MCP/LSP env + hook commands) substitutes real values. `substituteUserConfigInContent` (for skill/agent prose) substitutes a descriptive placeholder for sensitive keys and leaves unknown keys literal.
- **how:** Both read the same schema's `sensitive` flag. ## cc.15 Two-variable path contract: version-scoped ROOT vs persistent DATA

- **where:** /Users/tranquangdang21/Projects/claude-code-ref/src/utils/plugins/pluginOptionsStorage.ts:313-343 (substitutePluginVariables); pluginDirectories.ts:100-120 (getPluginDataDir)
- **what:** `${CLAUDE_PLUGIN_ROOT}` = the version-scoped install dir, recreated on every update. `${CLAUDE_PLUGIN_DATA}` = a persistent per-plugin dir under `plugins/data/<id>/` that survives updates.
- **how:** Both use function-form `.replace()` deliberately — ROOT so `$`-sequences in NTFS paths ($$ , $' , $` , $&) aren't interpreted as replacement patterns; DATA so the lazy `mkdirSync` only fires when the token is actually present. Both normalize backslashes on Windows.
- **solves:** Gives plugin authors a place to keep state (databases, caches) that does not get nuked on every plugin update, while keeping read-only plugin files clearly version-scoped. The `$`-in-path replacement bug is a real one that a naive `.replace(str, path)` hits immediately.
- **port effort:** Low effort, high value. The function-form `.replace()` comment is worth reading twice. | **idea only:** True
